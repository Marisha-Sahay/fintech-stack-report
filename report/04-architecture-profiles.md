## Architecture profiles

Thirteen companies publish enough to sketch their architecture end to end. Each profile gives the money path, the deployment topology, and the one choice that defines the design. Arrows mark the order a payment passes through components.

### Payment platforms

**Stripe.** *Money path:* payments API → edge checks (rate limiters, idempotency keys and API versioning, described 2017 to 2020) → internal services through Stripe's own mesh proxy → DocDB → card networks. Ledger checks money movement after the fact instead of sitting on the request path [@stripe-payments-api-2020; @stripe-rate-limiters-2017; @stripe-idempotency-2017; @stripe-mesh-proxy-2026; @stripe-ledger-2024]. *Topology:* AWS, with DocDB replica sets spread across availability zones and regions [@stripe-docdb-qcon-2025]. *Defining choice:* a verifying ledger off the hot path. "Ledger is our system of record and must remain an evergreen representation of truth" [@stripe-ledger-2024].

**Adyen.** *Money path:* stateless edge services → the payment processing layer, which calls risk, recurring and routing services before the payment goes out to the schemes → a local PostgreSQL queue → round-robin accounting clusters → streams to reporting [@adyen-design-duty-architecture-2021; @adyen-design-duty-accounting-2021]. *Topology:* its own data centers in Europe, the US, India, Singapore, Japan and Australia, accepting payments at several locations at once, with no public cloud for payment processing [@adyen-infrastructure-2026]. *Defining choice:* a stateless, write-restricted edge. "All our externally exposed systems are prohibited from writing to central databases" (2021) [@adyen-design-duty-architecture-2021].

**Block (Cash App).** *Money path:* Temporal workflows on every money transfer → each payment split into per-customer movements → Vitess routes each to its customer's MySQL shard → the Ledgering team's systems record it [@block-temporal-cashapp-2024; @block-remodeling-payments-2018; @block-job-ledgering-2026]. *Topology:* Cash App runs across availability zones in us-west-2, chosen "for its stability and low failure correlation". Square runs active in several AWS regions and shifts traffic between them regularly [@block-resilience-2025]. *Defining choice:* consistency over availability. "We will never compromise data consistency in exchange for availability" (2018) [@block-sharding-cash-2018].

**Uber.** *Money path:* order insertion service → immutable order store and Kafka → order processing service → User Account Store, with hot accounts batched → entity changelog and LedgerStore → a payment integration interface → external providers [@uber-gulfstream-2020; @uber-high-throughput-2026; @uber-zero-sum-2026]. *Topology:* active-active across regions as a stated goal (2018 and 2020), with standby cross-region consumers and balance storage on a multi-zone quorum. LedgerStore runs in Uber's own data centers [@uber-gulfstream-2020; @uber-ledgerstore-migration-2024]. *Defining choice:* two named sources of truth. "The two shared sources of truth across all services are the money order store and the entity balance store" [@uber-zero-sum-2026].

**Airbnb.** *Money path:* billing and pricing APIs → payment orchestration as a graph of idempotent steps over Kafka, using Orpheus → a processing gateway with a connector per processor. The ledger and reconciliation sit beside the path [@airbnb-payment-orchestration-2022; @airbnb-payments-platform-2016]. *Topology:* AWS, with several processors integrated "to achieve global coverage and payments redundancy" (2018) [@airbnb-transactional-integrity-2018]. *Defining choice:* "Every major workflow is divided into a directed acyclic graph (DAG) of retryable idempotent steps, each with well-defined behavior" [@airbnb-payment-orchestration-2022].

**Shopify.** *Money path:* card fields in an iframe → CardSink, which encrypts and tokenizes the card → checkout in the Rails monolith and a background job → CardServer and a processor adapter → acquirer, network and issuer [@shopify-flash-sale-talk-2022]. *Topology:* shops grouped into pods with fully isolated datastores (2018). Each pod is active in one region and replicated to a second, and a whole pod can fail over [@shopify-pods-2018; @shopify-flash-sale-talk-2022]. *Defining choice:* keeping card data away from the monolith. "We just don't let it see any card data in the first place" [@shopify-flash-sale-talk-2022].

### Neobanks and consumer fintech

**Monzo.** *Money path:* Mastercard → Monzo's own data centres → edge services on AWS → a Go card processor that calls account, financial crime and ledger services → the ledger → asynchronous events → daily reconciliation [@monzo-thousands-microservices-2023; @monzo-payments-safely-2022]. *Topology:* AWS across availability zones, a few owned data centres for scheme connections, and Stand-in, a separately written backup bank of 18 services on Google Cloud [@monzo-stand-in-2025]. *Defining choice:* a thin physical edge. "We run the absolute minimum compute possible to interface messages with our core platform" [@monzo-thousands-microservices-2023].

**Nubank.** *Money path (2017):* Mastercard → router → authorizer in Nubank's own data centers, with HSMs and fraud checks → Kafka to AWS → the customer's shard → double-entry service → balances back to the authorizers [@nubank-architecture-qcon-2017]. *Topology:* AWS, where each shard is a full copy of the infrastructure, plus a global section for cross-shard work. Authorization runs active-active in owned data centers [@nubank-architecture-qcon-2017]. *Defining choice:* authorization that does not depend on the cloud. "We don't need any cloud communication in order to authorize the transaction, that was important" [@nubank-architecture-qcon-2017].

**Revolut.** *Money path:* card network → card payments processor → card payment engine → Core Ledger and other core services → event store → financial crime and notification services [@revolut-xt25-slides-2025]. *Topology:* Google Cloud and Kubernetes, with four availability tiers from 99.5% to 99.99%, and an availability tier required for every component [@revolut-devops-qcon-2025]. *Defining choice:* fixed service types (frontend, flow and state). "Every service would have its own type predefined" [@revolut-qcon-architecture-2025].

**Starling.** *Money path (2018):* app → customer service stores the instruction and reduces the balance → payment service sends to Faster Payments → bank service records it in the ledger. Each step is keyed by an ID, stored first, and retried [@starling-cloud-bank-java-2018]. *Topology:* AWS from the start, with at least two instances of every service. Owned UK data centres hold the payment hardware and connect to AWS over Direct Connect. Engine now runs on Google Cloud and AWS [@starling-cloud-bank-slides-2018; @starling-card-processor-2022; @starling-engine-gcp-job-2026]. *Defining choice:* the database as a work queue. "The database becomes the repository of what work must be done" [@starling-cloud-bank-java-2018].

**Wise.** *Money path:* quote → transfer → pay-in → ledgers → payouts run as tasks → direct connections to local schemes such as InstaPay, Zengin and PIX [@wise-tech-stack-2025; @wise-tw-tasks-executor-2025; @wise-vendor-switching-2026]. *Topology:* AWS with centralized networking and more than 20 Kubernetes clusters, plus physical data centres in the UK, Hungary and Australia for scheme connections [@wise-tech-stack-2025]. *Defining choice:* side effects that run only after the business transaction commits. Tasks execute "only when business logic is successfully committed" [@wise-tw-tasks-executor-2025].

### Large scale and banks

**Ant Group.** *Money path:* request routed by user ID at the network entry to its unit → transaction service → payment service → accounting service, all in one TCC transaction → OceanBase [@ant-group-unitization-2026; @ant-group-seata-tcc-2019; @ant-group-oceanbase-history-2025]. *Topology:* units spread across three regions and five data centers, with a stated RPO of 0 and RTO under 30 seconds, and a Kubernetes cluster per unit [@ant-group-fingrade-arch-2026; @ant-group-unitization-2026]. *Defining choice:* "The core idea of unitization is to shard user requests at the network entry point, not just at the data layer" [@ant-group-unitization-2026].

**Capital One.** *Money path:* card processing at an external processor [@capital-one-10k-2023]. Transaction reads go from the mainframe through Lambda to a read-only DynamoDB store (2017) [@capital-one-serverless-transactions-2017]. *Topology:* all AWS since 2020, chosen because "If one region were to go down, we can stand up in another region on AWS" [@capital-one-cloud-migration-2024]. The virtual card number service runs active-active across East and West regions on DynamoDB global tables (2021) [@capital-one-dynamodb-resiliency-2021]. *Defining choice:* no database failover. "The application writes to the database in its region and the data is replicated by AWS keeping the regions in sync" [@capital-one-dynamodb-resiliency-2021].
